# 统一身份认证与会话托管（方案 B）—— 2026-10-23

## 1. 为什么不用「服务端账号密码登录」

实测中科大 SSO（`id.ustc.edu.cn`，2026-10-23 Playwright 抓包）：

| 环节 | 事实 |
|---|---|
| 页面 | 自定义 SSO（非 Apereo CAS）：隐藏 `<p id="login-croypto">`、`<p id="login-page-flowkey">` |
| 密码 | **AES 加密成 16 字节块**（key 来自页面 `login-croypto`），字段名 `password`；**不是 RSA** |
| 令牌 | `execution` = `login-page-flowkey`（`<uuid>_<base64 JWT>`），页面里没有 `execution` input |
| 风控 | 提交前 4 次上报：设备指纹、`itdr` verify token、**密码 SHA-1**、安全策略 |
| 二次认证 | **强制短信验证码**（`type=smsLogin`），成功的会话仍要 `trustDevice` |

→ 服务端全自动登录**既过不了短信，也会触发风控**。因此改为「半自动 + 会话托管」。

## 2. 半自动登录（`scripts/sso_login_browser.mjs`）

- 真实 Chromium 打开统一认证页（真指纹，不伪造）
- 两种模式：浏览器模式（你在窗口里输入，**密码不经过代码**）/ `--assisted`（终端提示、代填、不落日志）
- 成功后导出 CookieJar 到 `~/.xiaowo_sso_cookies.json`（**600**）
- 实测导出：12 条（`SOURCEID_TGC` 552B、`jw SESSION`、`rememberToken`、`deviceID` 等）

## 3. 会话托管（`services/session_vault.py`，方案 B）

服务端**不落地凭据**：

```
CookieJar → 精简（只留 id./jw. 的必要项）→ AES-256-GCM 加密 → base64url
  → 写【我们域】HttpOnly + Secure + SameSite=Lax + Max-Age 的 cookie（xiaowo_jw）
  → 每次请求带回 → 解包 → 灌进 requests.Session → 调教务 API → 用完即弃
```

- 实测体积：12 条 → 7 条 → **1830 字符**（浏览器上限 4096）
- 拒绝策略：篡改、错 key、过期、时钟倒流 → 一律视为无效会话（fail-closed）
- 配置：`XIAOWO_SESSION_VAULT_KEY`（为空则功能关闭）、`XIAOWO_SESSION_VAULT_TTL`（默认 43200s）

## 4. 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/v1/auth/sso_cookie` | 接收浏览器导出的 CookieJar → 先校验会话真能打通教务 → seal → `Set-Cookie` |
| `DELETE` | `/api/v1/auth/sso_cookie` | 清除托管会话（退出登录时调用） |

两个接口都走 `require_mutation`（CSRF + Origin 校验）；**不接收、不存储密码**。

## 5. 与西电 Traintime PDA 的取舍

| | Traintime（客户端 App） | 小蜗（Web，方案 B） |
|---|---|---|
| 凭据存放 | 设备 SharedPreferences（**密码明文**）+ `PersistCookieJar` | **用户浏览器 HttpOnly cookie 里的加密 TGT** |
| 服务端职责 | 无服务端 | 只做加解密与探测，不落库 |
| 二次认证 | 短信/企微码（人工） | 短信码（人工，浏览器内完成） |
| 反自动化 | 有滑块自动求解器（**不学**） | 不伪造指纹、不绕风控、不自动过验证 |

## 7. 已知边界

- **前端尚无「导入会话」入口**：当前只能脚本导出 + 接口导入；页面级完整体验需要加一个按钮（下一步）。
- 端点集成测试需在带 `fastapi` 的环境跑（本地无依赖）。
- 会话与 `trustDevice` 绑定学校侧策略；过期后需重新走一次半自动登录。
