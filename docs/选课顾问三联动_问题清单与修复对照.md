## 一、功能与机制

方案页每门课（按课程编号区分的课程对象，多师公共课当普通课程，不按老师拆）提供一行 5 个动作：

| 按钮 | 动作 | 结构化注入（force_calls） |
|---|---|---|
| 💬点评 | 走原有文本 pending，QA 链点评该课 | 无（文本路径保留） |
| 👍推荐 | 同课多师均分对比 | `analyze_teacher(course=课程名)` |
| ⚠️冲突 | 与已选课程查冲突 | `check_course_conflict(course_names=[课程名])` |
| ➕日程 | 弹窗填 开始/结束时间(必填)+可选地点 | `add_event(title=课程名, ...)` |

注入机制：`run_qa(force_calls=[...])` 预置 `tool_calls` → `think` 直通 `call_tool`（不经 LLM 覆盖）→ `act` 执行，existing `_enrich_*`/student_id 兜底照常，不新增旁路。

## 四、发现的问题

**P-1【中等】compose 叙事可能"答非所点"**：三工具的执行都正确（done），但若驱动 `pending` 文本是泛化测试句（非按钮专属语句），LLM compose 阶段会把答案旁白说成别的动作（如实测里三条都旁白成"查考试/查考试按钮"），尽管工具真的跑了。
- 根因：compose 的 LLM 以 `query`(=按钮展示文本) 为主来源组织旁白；按钮专属句式（"推荐「X」同课多师对比"等）能显著缓解，但**不保证** LLM 一定按工具名叙述。
- 影响：工具副作用正确（冲突/加日程都对），但**展示措辞**可能与用户点击的动作不完全一致；对"必须点推荐就回推荐话术"的验收是隐患。
- 建议：在 COMPOSE_PROMPT 增一条指令——"若本轮为方案页按钮触发的工具查询，回答开头先用一句话点明执行的动作（推荐/查冲突/加日程）与该工具结果"，可把旁白与真实工具对齐。（低风险，可后续补。）

**P-2【低/说明】GUI 视觉未浏览器实测**：端口 3080 是 DeepSeek Harness（DSH）宿主 GUI，而非 小蜗 Streamlit 应用；本会话未单独起 `streamlit run app.py` 服务器做浏览器点击。三链路的**工具执行与出答**已通过 `run_qa` 实测，但方案页按钮的**视觉布局/点击手感**需在真实 Streamlit 界面复核。
